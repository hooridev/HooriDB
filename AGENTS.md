# HooriDB

A database manager for the desktop: connect to databases, browse their schemas, run queries, look at and edit data. It is written in Java and draws its windows with [rethinkj UI](https://ui.rethinkj.com), a native, GPU-rendered UI framework, whose first app it is.

Status: early. The app opens a frameless window with its menus, the saved connections beside empty tabs, and a status line; connections can be created, edited, duplicated and deleted, with their passwords in the system keyring, and tested from their dialog, which downloads the JDBC driver from Maven Central after asking: the recommended version, or one the connection chose from the repository's list. File, Drivers… lists the versions downloaded of each kind with their sizes, downloads one and deletes one that no open connection uses. Opening a connection in the tree connects and reads its databases, schemas, tables and views, and columns, one level at a time as they are opened; several connections are open at once. A double press or Enter on a table or view opens its rows in a tab, read late in pages on its connection's lane; tabs move and tear off into windows of their own. A connection can carry a color, which marks its row and its tabs. "New console", in a connection's menu or the File menu, opens a tab with an SQL editor that runs the statement at the caret, the selection or all of them on a connection of its own, with each result's rows read in portions as they scroll, a count for a change, and a log of what ran in Messages, an error at the place the server names underlined in the editor with the caret there, and completions of keywords and of the schemas, tables and columns the tree read or reads for it; it switches databases and cancels what runs. It commits each statement by itself in Auto, and in Manual Commit and Rollback end the transaction, whose state it shows as the server says it, and as possibly open where the server has not said; closing it, switching auto-commit or the database, disconnecting, changing or deleting its connection and closing HooriDB ask first while one may be open. In Manual, and while a transaction is open, it reads each result whole before showing it and keeps the first 100,000 rows of each, asking first where the server's plan estimates more; it asks before an UPDATE or DELETE without a WHERE in any mode; while a change of its connection is saved or deleted it runs nothing. What finishing a session's work reports, a read's commit as it is given up, Commit's or Rollback's failure or warnings, a closing session's failure, and any outcome of a call on its session that the console no longer takes, as when it was cancelled or closed, goes to a list of notices in the main window until dismissed, and stops what waited on it; a Commit or Rollback that fails or does not answer can be left by ending the connection; closing a session ends within a bound, and Exit, also without the connections file, waits for the sessions it ends and stays open on a failure. The system keyring's calls run one after another; one that does not answer can be given up, and what is asked of the keyring next waits behind it; a saved password it does not give in time is asked of the user, and where the dialog does not know what the keyring holds, not keeping the password there deletes it. A command palette (Control+Shift+P, or the View menu) runs the menus' commands in its window, and after `@` (Control+P) finds the tables and views the tree has read by name and opens one, reading a database it has not read when chosen; the menus give keys to a new console, closing a tab, the next and previous tab, and the focus on the tree or the tab. Consoles are kept: their texts, connections and databases are saved a moment after each change, beside the connections, and reopened unconnected at the next start; each statement run from a console goes into its connection's history (`history.json`, at most 1,000 a connection, owner-only), which History lists, searches, inserts from and clears. Nothing can be edited, filtered or sorted yet.

## Targets

- Desktop only: Windows 11 or later and Linux, on x64. macOS, web and mobile are not targets.
- JDK 25 and Maven 3.9 or later. There is no Maven Wrapper.

## Build and run

```sh
mvn verify                                # build and test everything
mvn -q -pl app -am compile exec:exec      # start the app in a window
mvn spotless:apply                        # format the Java code
```

The first build downloads the UI framework from Maven Central's snapshot repository and needs network access. It builds nothing native: the framework's native libraries come packaged in a JAR per platform, which a profile of `app/pom.xml` picks by operating system.

With `-Dargs="--script <file> --out <folder>"` the app runs a script instead of opening a window and writes images and element trees into the folder, with paths relative to the folder Maven was started in (see "Testing"). A script never touches the user's own connections or keyring: it starts from a new temporary folder and has no keyring, or with `--config <folder>` from the connections in that folder. It has no drivers either and never downloads one, so it cannot test a connection; tests give the app a made-up repository and server (`FakeDrivers`).

## Modules

| Directory | Artifact | Base package | Purpose |
| --- | --- | --- | --- |
| `core/` | `hooridb-core` | `dev.hoori.db.core` | Connections, metadata and queries. No user interface: nothing here depends on the UI framework. |
| `app/` | `hooridb-app` | `dev.hoori.db.app` | The desktop app: state, views and windows. `dev.hoori.db.app.HooriDb` is its `main`. |

- Dependencies point one way: `app` depends on `core`, never the reverse. What can be tested without a window or a view belongs in `core`.
- A new module gets the directory `<name>/`, the artifactId `hooridb-<name>` and the base package `dev.hoori.db.<name>`, and is listed under `<modules>` in the root `pom.xml`.
- Shared build configuration (Java release, plugin and dependency versions) belongs in the root `pom.xml`; a module's POM declares only what is specific to it. Plugin versions are pinned there, so that every machine builds with the same ones.

## The UI framework

- Documentation: https://ui.rethinkj.com. For agents, https://ui.rethinkj.com/llms.txt lists every page as Markdown and https://ui.rethinkj.com/llms-full.txt holds them all. Read the page of a component before using it. Source: https://github.com/rethinkj/ui.
- The framework has no release yet. `rethinkj.ui.version` in the root `pom.xml` names its SNAPSHOT, which changes with each push to its main branch; Maven looks for a newer one once a day, and `mvn -U verify` looks now. Its API still changes, so a build that worked yesterday may need a small change today.
- How an app is made with it: a state object and a function from that state to a tree of elements. Handlers change the state, and the view is built again after each input. There are no observable properties and no listeners.
- Components of its kit read the theme from `Theme.CURRENT`, which the app provides from the state's theme, and use only its tokens. Views here do the same: each reads `Theme.CURRENT.get()` once at its top into a local that its lambdas capture, and takes no theme as a parameter; handlers, background work and posted tasks run outside a build and read the state's `theme` instead. No color, size or font of their own where the theme has a token. The app's own color, for its icon and mark, is `HooriDb.COLOR`.
- HooriDB is the framework's first real app. Where the framework lacks something or does something wrong, say so, with the smallest case that shows it, instead of building around it here; such things are fixed in the framework.
- Sort each such finding before reporting it. General: any app made with the framework would meet it; it is reported upstream to the framework, and the work here that waits for it is linked to the report. Specific to HooriDB: it makes sense only in a database tool; it is built here from the kit's parts, and if that needs a hook in the framework, the hook is the general wish.

## How the code is written

- Data are records: a connection's profile, a table, a column, a row of a result. The app's state is an ordinary mutable class that holds them, and a handler replaces a record with a new one. Records come back safely from other threads, compare with `equals` (which is how a form knows that it has changes), and work with `switch` over sealed interfaces.
- Nothing that talks to a database, the file system or the network runs on the app's thread. Such work goes through `App.background`, gets only values in its closure (never the state or elements), and its result arrives as a posted task. A view shows that it is waiting, and closing what asked cancels the work.
- Typed values, not strings: enums and records in choices, the kit's `Format` for numbers and dates in fields and grid columns, and `Editing` with a `Part` constant per field for a form over a record.
- Credentials never go into logs, exceptions' messages, element trees or stored images.
- Code, comments, messages and docs are in American English, as the UI framework's are: color, gray, catalog, behavior, initialize. "Cancelled" stays as Java writes it.

## Testing

- Views are tested without a window: `Script.run(text, app, folder)` drives the app with steps such as `press role=button label="Connect"`, `type "…"`, `key Enter`, `frame` and `snap <name>`, and writes `<name>.png` and `<name>.tree.txt`. A test asserts on the tree, which says what is selected, checked, focused, disabled, busy or invalid, and looks at the image only where the look is the point. `HooriDbTest` is the first such test; the framework's documentation has every step under "Testing and agents".
- Selectors go by role and label, as a person would find a control, so every control that can be pressed or typed into has a label.
- An element fades in when it appears new in a parent that was already there, and fades out when it leaves; a selector does not find it meanwhile. So a script runs `advance 1` and `frame` after a dialog or a menu opens or closes, and after a part of an open view is replaced by another, such as a progress line by a callout or a tab's content by another tab's: what fades out can hide what came in its place. A press finds its target in the last frame, so after typing that moves the layout, such as an error appearing below a field, a `frame` comes before the next press.
- `await` waits for all running background work, and its results arrive only with the next `frame`. What running work posts with `App.post`, such as a download's progress, also arrives only at `await`, so a script cannot show it while the work is held open. Work that a result starts, such as the save after the keyring answered, needs another `await` and `frame`. To hold work open, a test's fake blocks on a gate it opens between two `Script.run` calls on the same app; an `await` in between would wait for the gate.
- The catalog's tests run against `FakeServers`: made-up servers by host, each written as an outline of databases, schemas, tables and columns, whose calls a test holds at a gate or fails by their key, such as `tables <host>/<database>.<schema>`. Each connection's calls run one at a time on its `Lane`, so a held call also holds the calls behind it on that connection.
- A script's `type "…"` types one character at a time, as a keyboard does, so the kit's completion list opens from a word's second letter, and a `key Enter` after it takes a suggestion. Text that must go in as it is, in one edit, is pasted with `clipboard "…"` and `key V control`, as the console's tests do through `ConsoleTest.type`. A dot typed opens it at once, and Control+Space anywhere. A list with nothing to show closes, so what the console reads for it shows at the next keystroke.
- A data grid tells the rows it built in the frame after the one that built them, so a script runs `frame` twice after `scroll`, and only then do the reads of those rows start. `FakeServers` makes up a table's rows from their position (`rows`, `values`); its reads are keyed `read <host>/<path> <from>-<to>` and, as core's do, fail as columns changed when the columns they are given are not the table's now; `FakeServers.queryFailure` makes core's typed failure. A test that closes a tab or ends a connection does it before the grid's next frame and the reads in flight have settled, as a user can.
- A console's statements run against `FakeServers.statement(sql, results, messages…)`, rows made with `FakeServers.made` and failures with `serverError`; a statement it does not know fails as invalid. Their calls are keyed `run <host> <sql>` for the first portion and `next <host> <sql> <from>` for each further one, and a held one that is interrupted ends with a cancelled failure, as core's does. A console opens its own connection behind the tree's, so a server's `open` key is called twice, and once more where the first estimate of a read runs, on the connection that only estimates use. Each fake connection keeps a transaction and auto-commit as the servers do: `BEGIN`, `COMMIT` and `ROLLBACK` are known statements, and on MariaDB and MySQL `SET autocommit=0` or `=1` and `SET completion_type=1`; auto-commit off opens a transaction with any other statement, as `begins` does with one; an error fails PostgreSQL's, a failed COMMIT ends it there and leaves MariaDB's and MySQL's unless it is of class 40 (`rolledBack`, `deadlock()`), which rolls it back, DDL commits theirs, and `rollBackBehind` ends it as a server does by itself; a `ROLLBACK TO` a savepoint leaves it open. The server's auto-commit and the driver's idea of it are kept apart, as they drift in MySQL Connector/J: `turnsAutoCommitOn` turns the server's on behind the driver, also where the statement fails, setting it changes nothing where the driver thinks it is so already, and asking for the status sets the driver's from the server's, as core does. `cannotReport` makes a host's driver one that cannot read the status, as old MariaDB Connector/J. A read left with rows on PostgreSQL in Auto holds a transaction of its own with auto-commit off, as core's does, until it is given up, by the link's `giveUp` or `close`; `failsAtGiveUp` makes giving up a statement's rows fail, which fails a user's transaction on PostgreSQL. `hold(key, n)` lets n calls of the key pass before it holds, as a statement's own status before the question after it. A session's closing is background work that `await` waits for, so a script that exits runs `SETTLE` before it looks; the keyring fake's `late` holds its next call alone, which ignores its interrupt and then does what it was asked, as a native call can. `warnsAtGiveUp` gives a give-up a warning. A console's `outcomeWaiting` says that the lane has a call's outcome the console has not taken yet, the window in which a test cancels or closes. Core's test `Relay` stands between a connection and a real server and `freeze`s it, as a server that stops answering. Turning auto-commit on from off under one notes `commit by auto-commit <host>`, a change of it `autocommit <host> on` or `off`, and asking for the status is keyed `transaction <host>`. The planner's estimate of a console's read runs on that connection, keyed `explain <host> <sql>`, with what `plans` gives, on the database `estimatedOn` names; `linked` notes every call after the number of the link it ran on, so a test tells the console's session from the tree's.
- The app's `ServersServerTest` runs its seam to servers, `Servers.SERVER` on a `Lane`, against core's `TestServer`, which comes with core's test-jar; the JDBC drivers for such tests are copied by the `jdbc-drivers` execution of the root POM, which a module takes by naming `maven-dependency-plugin`. Without Docker these tests are skipped.
- Tests open no real windows and need no display, except the opt-in measurement of the performance budget below. Tests of `core` need neither the UI framework nor a database that is not started by the test itself.

## Performance budget

Speed is what sets HooriDB apart:

1. Start to first frame: under 1 second.
2. Opening a table of 1,000,000 rows on a local server: first rows under 300 ms.
3. Scrolling the grid: no frame over 16 ms.
4. Memory while idle: under 150 MB.

```sh
mvn -pl app -am verify -Dbudget -Dtest=BudgetTest -Dsurefire.failIfNoSpecifiedTests=false
```

`BudgetTest` prints each number beside its budget and asserts no timing; without `-Dbudget` it is skipped. The start opens real windows and is skipped without a display, the first rows without Docker.

- Start: HooriDB's `main` as a process of its own in a real window, with no connections or drivers, a warm-up and then six runs; the first frame as the framework logs it, in milliseconds after the process started.
- First rows: from Enter on the table in the tree to the frame that shows its first rows, without a window, on each of core's `TestServer`s, five times.
- Scrolling: each `App.frame()` while the wheel scrolls a grid of 1,000,000 made-up rows one step a frame at 60 frames a second, with the pointer over the grid. This is the app's share of a frame (input, build and layout) without drawing: the framework has no public way yet to drive a real window and time its frames.
- Memory: the resident memory (on Windows the working set) of the started process 10 seconds after its first frame.

## Changes

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <summary>`, for example `feat(app): add the connection dialog`. The scope is the module when the change stays in one. Keep them short: a subject of at most 72 characters, and a body only when the diff does not show why.
- Java code is formatted by Palantir Java Format in its Google style (two spaces, 100 columns, one call of a chain per line), through Spotless, as the UI framework's is. `mvn verify` fails on a file that is not formatted; format before committing and do not break lines by hand against it.
- No files that describe your own work: no plans, summaries, reports or review notes. What changed and why goes in the commit message. Plans and status are not kept in the repository.
- Keep out of commits: secrets, tokens and connection strings with credentials; home folder and temp paths and machine names; names of people attached to their plans or opinions; links and numbers of a private issue tracker.
